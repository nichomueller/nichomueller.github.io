Software practice

From Research Methods to Scientific Tools

Scientific software is most valuable when it makes a research idea accessible beyond the original study. I aim to build code that is clear enough to understand, robust enough to reuse, and flexible enough to extend to new problems and applications.

That means paying attention to the architecture as well as the algorithms: keeping physical assumptions and numerical methods clearly separated, providing examples that demonstrate how the methods are intended to be used, testing important behaviour, and profiling performance.

For me, these are not separate from the research. They are part of turning a mathematical method into a practical scientific tool—one that can be tested, extended, and applied to problems beyond the example that motivated it.

Performance note

The optimization behind GridapROMs.jl that isn't parallelism

Solving a PDE at hundreds of parameter values is usually implemented as an outer loop over parameters and an inner loop over mesh cells, reallocating the local element caches every time the outer loop advances. That's the default in most finite element codes, and it's the first thing that gets expensive as the parameter count grows.

GridapROMs.jl flips the nesting: cells are the outer loop, and every parameter value at a given cell is handled together through a lazy structure called a ParamBlock, built on top of Gridap's existing lazy-array machinery. Element caches get allocated once per cell and reused across all parameters, instead of once per parameter per cell.

One counterintuitive result from the paper: memory use stays roughly flat as the mesh gets finer, even though a finer mesh means far more elements to loop over. The memory cost comes almost entirely from the local caches, which don't grow with mesh resolution the way a naive implementation's element storage would; refining the mesh mostly costs wall time, not memory.

Data assimilation note

Why reservoir computing fits naturally inside a bias-aware Kalman filter

Kalman filters assume the innovation, the gap between an observation and the model's prediction, is zero-mean Gaussian. A structural bias in the sensor or the model breaks that assumption outright, and the filter never really converges: it keeps correcting toward a systematically wrong target. Bias-aware filtering fixes this by modelling the bias itself, but that model needs to be retrained as new data comes in, and its Jacobian with respect to the forecast state is needed at every analysis step.

As suggested in Novoa et al., an echo state network is a good fit for this because only the linear readout is trained; the recurrent reservoir weights stay fixed and random. Training reduces to a ridge regression problem instead of anything resembling backpropagation through time, which is cheap enough to redo repeatedly (Opals.jl uses a recycle-validation strategy for this), and the Jacobian of a linear-readout network is trivial to compute, which is exactly what the bias-aware correction step needs.

The Opals.jl paper demonstrates this on a Van der Pol oscillator with a sensor corrupted by a cosine bias term. The bias-unaware EnKF diverges, since the biased observations never let the innovation settle into the zero-mean Gaussian the filter assumes. Adding the ESN-based bias correction fixes that directly: the innovation distribution becomes Gaussian again, and the filter converges on the true state and parameters.
